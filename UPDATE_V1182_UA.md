# Установлення АМПасадори v1.18.2 з перевіркою

> Поточна підтверджена production-база: v1.18.1, Alembic `20260921_0014`. Нова збірка v1.18.2 **містить міграцію**, тому прямий запуск її коду на старій схемі БД недопустимий. Не виконуйте вручну `Base.metadata.create_all()` або `ALTER TABLE` — міграціями керує тільки Alembic.

1. Збережіть поточний Git-коміт, перевірте чистоту робочої копії (`git status`), доступність production, бота й черги. Отримайте перевірену резервну копію PostgreSQL через GitHub Actions → **AMP Verified Backup** (відновлення в ізольованій БД, не лише capture).
2. Створіть окрему гілку від актуальної `main` (наприклад `release/v1.18.2`). Архів має внутрішній каталог `amp_bot_v1182/`. Розпакуйте у тимчасовий каталог, перевірте `VERSION.txt`, скопіюйте в репозиторій без видалення `.git`, `.env`, `.venv`, `data`, `uploads`, `media` та історичних файлів. **Не використовуйте `rsync --delete`** без перевірки списку видалень.
3. Встановіть залежності з `requirements-dev.txt` у Python 3.13. Виконайте `python -m compileall -q app scripts migrations tests`, `python -m scripts.production_preflight`, `pytest -q --ignore=tests/integration` та `pytest -q tests/integration` у середовищі CI з PostgreSQL 16. Перевірте саме тест оновлення **з `20260921_0014` до `20260925_0015`**, downgrade/upgrade round-trip і schema drift.
4. Після успішних перевірок опублікуйте окрему гілку, створіть Pull Request. Перевірте зміни, резервну копію і лише після цього об'єднайте в `main`. `.github/workflows/ci.yml` автоматично запускає production-деплой із `main` після успішного CI. Не запускайте паралельно ручний Heroku-деплой.
5. Після завершення workflow перевірте `heroku run -a amp-bot-ver-1-5-0 -- cat VERSION.txt` (очікується `1.18.2`), `heroku run -a amp-bot-ver-1-5-0 -- alembic current` (очікується `20260925_0015`), процеси `web` і `worker`, а також фактичну адресу через `heroku apps:info`. Перевірте `/health/live` і `/health/ready` **на дійсному домені** Heroku, а не за короткою здогадною адресою.
6. У вебпанелі створіть тестову подію з майбутнім часом і два індивідуальні квести: ручний та автоматичний QR із прив'язкою до події. У тестовому середовищі перевірте своєчасне сканування, повторне сканування без дубля XP, запізнення, звичайний ручний квест, зміст повідомлень, завантаження Excel/Word/PDF і безпечне відображення кирилиці. Не створюйте тестову участь/XP реальних користувачів у production.

## Відкат

Перед відкатом зафіксуйте наявні нові дані. Оскільки v1.18.2 додає схему, **простий відкат коду до v1.18.1 без перевірки сумісності, журналу міграцій і резервної копії не є повним відкатом**. Не виконуйте автоматичне `alembic downgrade` на production і не відновлюйте стару БД, не оцінивши втрату нових даних. Рішення щодо відкату — після аналізу логів, схеми й стану користувацьких транзакцій.
